# Common Causes of Mail Loops and How to Fix Them

A mail loop occurs when at least two transport systems repeatedly hand the same message back and forth. Neither system recognizes itself as the final destination, but both identify an ostensibly suitable next hop. The loop ends only when a server determines that the permitted number of transport hops has been exceeded and generates an NDR.

In Exchange, two messages are particularly informative:

- `554 5.4.6 Hop count exceeded - possible mail loop` is typically generated by the local Exchange server.
- `554 5.4.14 Hop count exceeded - possible mail loop ATTR34` is generated by Exchange Online.

The hop limit is not the cause, but rather the safeguard against endless repetition. Increasing it therefore fixes nothing. The goal is to find the point at which the message is returned to a system it has already passed through, contrary to the intended destination architecture.

## Recognizing the Loop Pattern in the Header

The NDR and the complete original message headers should be saved before making any changes. `Received` lines are read from bottom to top: the lowest line is the earliest documented hop, and the topmost line is the most recent.

A loop usually appears as a recurring sequence:

```text
Internet
  → Exchange Online Protection
  → Mailgateway
  → Exchange Online Protection
  → Mailgateway
  → Exchange Online Protection
  → ...
```

Not every Microsoft hostname that appears multiple times is already a loop. Exchange Online processes messages internally through multiple transport roles. What is suspicious is a repeated return between the same administrative boundaries, for example between Exchange Online and an on-premises gateway. Timestamps, sending IP address, receiving host, and `Message-ID` help identify the cycle unambiguously.

For the initial analysis, answer these questions:

1. Which system generated the NDR?
2. Which two or three hops repeat?
3. Which system should have delivered the message finally?
4. Based on which domain, recipient, connector, or rule decision was it forwarded?
5. What change most recently affected mail flow?

## Diagnosing in Exchange Online

With `Get-MessageTraceV2`, you can investigate processing from the past 90 days; each query may cover no more than ten days. A narrow time window and the specific recipient address produce the most useful results:

```powershell
$start = (Get-Date).AddHours(-2)
$end = Get-Date
$recipient = "user01@contoso.com"

$trace = Get-MessageTraceV2 `
    -RecipientAddress $recipient `
    -StartDate $start `
    -EndDate $end `
    -ResultSize 5000

$trace |
    Select-Object Received,SenderAddress,RecipientAddress,Subject,
        Status,FromIP,ToIP,MessageTraceId,MessageId |
    Sort-Object Received
```

The details of a match show individual transport events:

```powershell
$trace | ForEach-Object {
    Get-MessageTraceDetailV2 `
        -MessageTraceId $_.MessageTraceId `
        -RecipientAddress $_.RecipientAddress
} | Format-Table Date,Event,Action,Detail -AutoSize
```

Next, review the domain, recipient, and connectors together:

```powershell
Get-AcceptedDomain |
    Format-Table Name,DomainName,DomainType,MatchSubDomains -AutoSize

Get-EXORecipient -Identity $recipient |
    Format-List DisplayName,RecipientTypeDetails,PrimarySmtpAddress,
        ExternalEmailAddress,EmailAddresses

Get-OutboundConnector -IncludeTestModeConnectors |
    Format-List Name,Enabled,ConnectorType,RecipientDomains,SmartHosts,
        UseMXRecord,RouteAllMessagesViaOnPremises,TlsSettings

Get-InboundConnector |
    Format-List Name,Enabled,ConnectorType,SenderDomains,SenderIPAddresses,
        TlsSenderCertificateName,RequireTls,RestrictDomainsToIPAddresses,
        RestrictDomainsToCertificate
```

What matters is not whether an individual object looks plausible. The domain type, actual recipient type, and applicable connector must all describe the same destination.

## Diagnosing in On-Premises Exchange

In a hybrid environment, check the same recipient on-premises as well. The queries distinguish between a genuine local mailbox, a RemoteMailbox, and a MailUser:

```powershell
Get-Recipient -Identity $recipient |
    Format-List DisplayName,RecipientType,RecipientTypeDetails,
        PrimarySmtpAddress,EmailAddresses

Get-Mailbox -Identity $recipient -ErrorAction SilentlyContinue |
    Format-List RecipientTypeDetails,ServerName,Database,PrimarySmtpAddress

Get-RemoteMailbox -Identity $recipient -ErrorAction SilentlyContinue |
    Format-List RecipientTypeDetails,PrimarySmtpAddress,RemoteRoutingAddress

Get-MailUser -Identity $recipient -ErrorAction SilentlyContinue |
    Format-List RecipientTypeDetails,PrimarySmtpAddress,ExternalEmailAddress
```

For the transport path, you need Send and Receive connectors as well as the tracking logs:

```powershell
Get-SendConnector |
    Format-List Name,Enabled,AddressSpaces,DNSRoutingEnabled,SmartHosts,
        SourceTransportServers,CloudServicesMailEnabled,TlsDomain

Get-ReceiveConnector |
    Format-List Identity,Enabled,Bindings,RemoteIPRanges,PermissionGroups

$servers = Get-ExchangeServer |
    Where-Object { $_.IsMailboxServer -or $_.IsHubTransportServer }

$servers |
    Get-MessageTrackingLog `
        -Start $start `
        -End $end `
        -Recipients $recipient `
        -ResultSize Unlimited |
    Select-Object Timestamp,ServerHostname,ClientHostname,Source,EventId,
        ConnectorId,Sender,Recipients,MessageId,NetworkMessageId |
    Sort-Object Timestamp
```

A `SEND` to Exchange Online followed by another `RECEIVE` for the same message from Exchange Online makes the return visible. `MessageId` and `NetworkMessageId` help prevent different test messages from being confused with each other.

## The Most Common Causes at a Glance

| Pattern | Typical Cause | Resolution |
| --- | --- | --- |
| Unknown recipients bounce between two systems | The Accepted Domain is set to `InternalRelay`, but both sides forward unknown recipients | Define clear responsibility; use `Authoritative` when delivery is entirely to EXO, or define a single final hop for a split domain |
| EXO sends to on-premises Exchange, which immediately sends back to EXO | The hybrid connector or Centralized Mail Transport no longer matches the mailbox location | Check the HCW configuration and `RouteAllMessagesViaOnPremises`; disable the outdated centralized route or correct local recipient resolution |
| A message bounces between EXO and a security, signature, or encryption gateway | Returning messages meet the outbound rule again | Use the header set by the gateway or the documented loop-prevention mechanism as an exception; authenticate inbound and outbound connectors unambiguously |
| Only one recipient is affected | Outdated or incorrect `targetAddress`, incorrect RemoteMailbox type, or conflicting proxy addresses | Determine the source of authority, correct the recipient object there, and synchronize it |
| Only forwarded messages loop | A transport rule, mailbox forwarding, or Inbox rule addresses the original path again | Disable the rule, correct the destination, and define a robust exception |
| Only one subdomain or application is affected | The parent domain does not correctly cover the subdomain in the expected connector path | Configure the subdomain explicitly as an Accepted Domain and in the appropriate Send Connector |
| All messages loop after a gateway or DNS change | The smart host or MX points to the sending system's inbound endpoint | Correct the next hop and check DNS, NAT, and load balancer targets separately |

## Cause 1: Incorrect Accepted Domain Type

An authoritative domain means that all valid recipients for that domain are known in the Exchange organization; unknown recipients are rejected. An Internal Relay domain means that some recipients are located in another system and must be forwarded through a Send or Outbound connector.

The problematic configuration occurs when Exchange Online sends unknown recipients to an on-premises system and that system also does not handle the same domain conclusively, instead returning it to Exchange Online via MX or a smart host.

```powershell
Get-AcceptedDomain -Identity contoso.com |
    Format-List DomainName,DomainType,MatchSubDomains
```

If all recipients are in Exchange Online after a migration is complete, `Authoritative` is usually the correct target state:

```powershell
# Run only after fully reviewing recipients and routing.
Set-AcceptedDomain -Identity contoso.com -DomainType Authoritative
```

For a genuine split domain, `InternalRelay` may be correct. However, this requires a clear connector to the system that knows the remaining recipients. This destination must not send unknown addresses back to the starting point.

## Cause 2: Overlapping Hybrid Connectors and Centralized Mail Transport

Centralized Mail Transport deliberately routes outbound Exchange Online messages through on-premises Exchange. This is useful for certain compliance requirements, but it creates additional transport paths. If the option remains active after a migration even though the on-premises system sends messages back to Exchange Online via its own MX, a loop can occur.

```powershell
Get-OutboundConnector -IncludeTestModeConnectors |
    Format-Table Name,Enabled,ConnectorType,RouteAllMessagesViaOnPremises,
        RecipientDomains,SmartHosts,UseMXRecord -AutoSize
```

Multiple connectors with overlapping scopes are also suspicious. Microsoft recommends a dedicated on-premises connector for hybrid mail flow; repairing the configuration through the Hybrid Configuration Wizard is often safer than making isolated individual changes.

If Centralized Mail Transport is demonstrably no longer needed, the setting can be disabled specifically:

```powershell
# Only after reviewing compliance and gateway requirements.
Set-OutboundConnector `
    -Identity "Outbound to On-Premises" `
    -RouteAllMessagesViaOnPremises:$false
```

## Cause 3: A Gateway Processes Its Returned Messages Again

In an in-and-out scenario, Exchange Online sends a message to an additional service for signing, encryption, or archiving. The service then returns it to Exchange Online. The outbound rule must recognize the returned message; otherwise, it is sent to the service again.

Start by checking all rules that select connectors, redirect recipients, or evaluate headers:

```powershell
Get-TransportRule |
    Sort-Object Priority |
    Format-List Name,State,Mode,Priority,FromScope,SentToScope,
        RedirectMessageTo,RouteMessageOutboundConnector,
        SetHeaderName,SetHeaderValue,ExceptIfHeaderContainsMessageHeader,
        ExceptIfHeaderContainsWords
```

The specific exception must follow the gateway vendor's documentation. A header set by the service that cannot be spoofed as trustworthy from the internet is common. In addition, inbound connectors should identify the service by certificate or fixed sender IP address. A blanket exception for all messages that appear “internal” is too broad.

## Cause 4: Recipient Object and Actual Mailbox Are Not in the Same Location

An object can appear in Exchange Online as a `MailUser` even though the active mailbox is on-premises. In a synchronized hybrid environment, this is not automatically a duplicate. Nor does a `ExternalEmailAddress` that matches the primary SMTP address alone prove a misconfiguration.

The combination of all queries is decisive:

- A local `Get-Mailbox` returns a result: the active mailbox is on-premises.
- A local `Get-RemoteMailbox` returns a result: the managed destination is in Exchange Online.
- `Get-EXOMailbox` returns a result: a genuine mailbox exists in the cloud.
- `Get-EXORecipient` returns only a MailUser: the object is a routing destination, not a cloud mailbox.

Problems include outdated objects after a migration, incorrect remote routing domains, or manually configured `targetAddress` values whose domain routes back through the same transport path. Make changes at the source of authority: in synchronized environments, use Exchange management tools on-premises rather than directly editing individual attributes in Exchange Online.

## Cause 5: Forwarding and Transport Rules Form a Loop

A rule can redirect from address A to B, while B sends back to A through a second rule, mailbox forwarding, or an external system. Such loops often affect only individual recipients or message types.

```powershell
Get-TransportRule |
    Sort-Object Priority |
    Select-Object Name,State,Mode,Priority,RedirectMessageTo,
        BlindCopyTo,AddToRecipients,RouteMessageOutboundConnector

Get-Mailbox -ResultSize Unlimited |
    Select-Object DisplayName,PrimarySmtpAddress,
        ForwardingAddress,ForwardingSmtpAddress,DeliverToMailboxAndForward

Get-InboxRule -Mailbox user01@contoso.com |
    Select-Object Name,Enabled,Priority,ForwardTo,RedirectTo,ForwardAsAttachmentTo
```

The fix is not simply to disable a rule temporarily. The complete chain must be resolved, and rules for external services require an exception that reliably recognizes messages already processed.

## Cause 6: MX, Smart Host, or Subdomain Points Back

A gateway may require a different next hop internally than external senders do. If it simply uses the public MX for forwarding, that MX may point back to the gateway itself. The same issue occurs when a smart host routes back to its own listener through NAT or load balancing.

```powershell
Resolve-DnsName -Type MX contoso.com
Resolve-DnsName -Type MX app.contoso.com

Get-SendConnector |
    Format-List Name,AddressSpaces,DNSRoutingEnabled,SmartHosts
```

Subdomains deserve separate review. Microsoft documents cases where an application subdomain must be explicitly created as an Internal Relay domain and synchronized to the Edge systems:

```powershell
New-AcceptedDomain `
    -Name "app.contoso.com" `
    -DomainName app.contoso.com `
    -DomainType InternalRelay

Start-EdgeSynchronization
```

These commands are not a universal fix. They are appropriate only if `app.contoso.com` is actually delivered outside the Exchange organization and the Send Connector has an unambiguous next hop.

## Safe Procedure During an Active Loop

During the incident, first stop the multiplication. Depending on the architecture, either carefully disable the triggering transport rule or specific connector, or have the gateway hold the affected queue. Export the configuration and message samples beforehand.

Then test with exactly one sender, one recipient, and a clearly identifiable subject line. Trace the message end-to-end through headers, Message Trace, and local tracking logs. Only once it reaches the intended destination should mail flow be gradually reopened.

Not recommended:

- Increasing hop limits
- Changing multiple connectors at the same time
- Switching Accepted Domains between `Authoritative` and `InternalRelay` speculatively
- Reinjecting a problematic queue repeatedly without verification
- Correcting synchronized Exchange attributes directly in AD or Exchange Online
- Disabling TLS, IP, or certificate checks as a supposed quick fix

## Final Verification

After the correction, the documentation should contain exactly one statement for each relevant domain: Which system knows the recipient, which connector applies, and which host is the final next hop?

Technical acceptance includes at least:

- External and internal test messages
- An unknown recipient in the same domain
- Recipients on each side of a genuine split domain
- An outbound message with the gateway or Centralized Mail Transport enabled
- Headers without a recurring hop sequence
- Message Trace with `Delivered` or the expected handoff
- Local tracking without another `RECEIVE` after a `SEND` to the same destination
- Connector validation for all connectors still required

A resolved mail loop is not complete merely because the test email arrives; unknown recipients and alternative mail flow paths must also terminate as defined. That is where most recurrences occur.
